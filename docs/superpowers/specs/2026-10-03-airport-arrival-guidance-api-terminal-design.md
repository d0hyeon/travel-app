# 공항 도착 안내: 인천 운항 API 터미널 기준 전환

`2026-09-21-airport-arrival-guidance-design.md`의 일부 규칙을 대체하는 후속 설계다. 기존 문서는 이력을 위해 수정하지 않으며, 아래에 적은 항목만 이 문서가 우선한다. 적지 않은 항목은 기존 문서를 따른다.

## 배경

기존 설계는 안내 대상 판단과 혼잡도 조회의 터미널을 **탑승권에 입력된 값**(OCR 또는 수동 입력)에서 얻었다. 이 값은 인식 오류나 오입력이 가능하고, 당일 터미널이 바뀌어도 따라가지 못하며, 일행 티켓의 값이 하나라도 다르거나 비면 안내가 사라진다. 탑승권을 올리지 않은 항공편은 안내 대상이 되지 못한다.

인천 운항 현황 API는 항공편마다 `terminalid`를 준다. 2026-10-03 실호출(8,435건, D+0~D+6)에서 `terminalid`는 전 구간 100% 채워져 있었고 값은 `P01`·`P02`·`P03` 셋뿐이었다. 코드셰어 편(Slave 4,457건)의 터미널은 마스터 편과 전부 일치했다. 반면 `gatenumber`는 D+0에만 채워져 판단 근거로 쓸 수 없다.

## 결정

1. 시스템이 신뢰하는 터미널은 인천 운항 API 값이다. 탑승권 터미널·게이트·좌석의 입력과 OCR은 기록·표시용으로 남긴다(비인천 공항, 조회 범위 밖의 표시 폴백).
2. 해외 출발 안내는 **인천 출발편만** 만든다. 비인천 출발 해외편은 안내하지 않는다. 기존에는 출발 공항과 무관하게 인천 혼잡도로 계산하던 결함이 있었다.
3. 국내선 안내(한국공항공사 혼잡도)는 변경하지 않는다. 국내선 경로는 계속 탑승권 터미널을 쓴다.
4. 인천 터미널 코드 해석: `P01` → 1터미널(T1), `P02` → 1터미널 탑승동(T1), `P03` → 2터미널(T2). 승객예고·실시간 혼잡도는 T1/T2 기준이다.
5. 화면 표기: `1터미널`, `1터미널(탑승동)`, `2터미널`. Edge 응답은 인천 원본 코드를 내리고, 라벨 변환은 도메인의 `toTerminalLabel` 하나가 맡는다.
6. 대기시간·대기인원 표시와 권장 도착 시각의 실시간 보정은 하지 않는다. 안내가 갑자기 바뀌면 신뢰가 떨어진다.

## 이전과 이후

| | 이전 | 이후 |
|---|---|---|
| 터미널 출처 | 탑승권 `terminal` (일행 전원 일치 필요) | `trip_transport_flight_status.terminal` (인천 API `terminalid`) |
| T1/T2 판정 | 문자열에 "2"가 있으면 T2 | `P01`·`P02` → T1, `P03` → T2 |
| 푸시 예약 자격 | 해외 + 티켓 터미널 입력·일치 | 해외 + 인천 출발 + 결항 아님 |
| 터미널 변경의 예약 재평가 | 대상 | 대상 아님 (예약은 터미널과 무관, 발송 시점에 확인) |
| 안내 대상 공항 | 출발 공항 무관 | 해외는 인천 출발만 |
| 운항 상태 감시 범위 | 출발 24시간 이내 | 저장은 출발 6시간 후부터 D+6, 알림은 출발 24시간 이내 |
| 클라이언트 운항 상태 조회 | 인천 API 직접 호출(공항 하루치 전량) | `trip_transport_flight_status` 읽기 |
| 안내 카드 터미널 표기 | 탑승권 원문 뒤에 "터미널" | 라벨(`1터미널` 등), 국내선은 기존 그대로 |

감시 범위를 넓히는 이유: 푸시는 출발 전날 18:00에 나가는데, D일 18:00 이후 출발편은 그 시점에 출발까지 24시간이 넘어 감시 대상이 아니었다. 대상이 아니면 저장된 터미널이 없다. API 호출은 대상이 있으면 5분에 1회(출발·도착 목록 각 1회)로 대상 수와 무관하므로 범위를 넓혀도 호출 횟수가 크게 늘지 않는다.

## 책임 경계

- `flight-status-watch`: 인천 API 결과를 관측값으로 저장한다(터미널 포함). 알림은 출발 24시간 이내 편에만 판단한다.
- `trip_transport_flight_status`: **외부 관측값**(현재 상태: 종류, 예정·변경 시각, 게이트, 터미널)과 **푸시 이력**(`last_notified_*`, `prev_gate`) 두 역할을 한 행에 둔다. 책임이 과해 보이나 현재는 분리하지 않으며, 이후 "푸시 컬럼 분리" 작업 후보로 둔다.
- 공항 도착 안내 Edge: 저장된 운항 상태의 터미널을 읽어 혼잡도를 조회하고 판단 결과만 내린다. 인천 API를 직접 호출하지 않는다.
- 화면: 원본 코드를 라벨로 바꿔 표시한다. 클라이언트도 같은 테이블을 읽는다.

## 영향과 한계

- 운항 상태 행이 아직 없는 편(새로 등록, 첫 감시 전)은 안내가 없다. 최대 5분이다.
- 클라이언트의 운항 상태는 최대 5분 늦을 수 있다. 새 편은 첫 감시 전까지 값이 비어 있다.
- 출발 후 6시간이 지나면 행이 갱신되지 않아 마지막 값이 남는다.
- 인천 도착편 감시는 이번에 건드리지 않는다(후속에서 제거 예정). 도착편 행에도 `terminal`이 기록되지만 도착 터미널이며 안내는 인천 출발편만 읽는다.
- 승객예고 API는 `selectdate` 0·1만 유효하다. 2 이상은 오류가 아니라 **오늘 데이터를 돌려준다.** 호출부는 D+0·D+1만 넘긴다.

## 터미널을 얻지 못하는 경우

실호출에서 `terminalid`가 비어 온 항목은 없었으므로, API가 값을 안 주는 상황은 재현되지 않았다. 안내가 만들어지지 않을 수 있는 실제 경로는 다음이다.

- 사용자가 적은 편명·항공사 코드가 API 목록과 맞지 않아 운항 상태 행이 만들어지지 않은 경우
- 항공사 코드나 편번호가 비어 있어 감시 대상에서 제외된 경우
- 푸시 발송 시점까지 첫 감시가 돌지 않은 경우

모두 `terminal`이 없는 것으로 취급해 안내와 푸시를 만들지 않으며, 빈 푸시는 보내지 않는다.

## 검증 기준

- 해외 인천 출발편은 탑승권 터미널 없이도 운항 상태 터미널로 안내가 만들어진다.
- 해외인데 인천 출발이 아니거나 운항 상태 터미널이 없으면 안내와 푸시가 없다.
- `P01`·`P02`는 T1, `P03`은 T2로 혼잡도를 조회한다. 그 밖의 값은 조회하지 않는다.
- 출발 24시간보다 먼 편은 저장은 되고 알림은 나가지 않는다. 24시간 안에 들어오면 정상적으로 판단한다.
- 국내선은 탑승권 터미널로 기존처럼 동작한다.
- 안내 카드는 `1터미널`·`1터미널(탑승동)`·`2터미널`로 표시한다.
- 클라이언트의 터미널·게이트·지연·변경 출발 시각 표시가 인천 API 직접 조회 때와 같다.
